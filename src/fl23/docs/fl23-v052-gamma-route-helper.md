# 0.5.2：FL2／FL3 的 Gamma 一直沒被讀到（路由 helper 改寫 color 索引）

## 現象

0.5.1 上機後，三個場景各拍 ST／FL2／FL3，與 Adobe `Camera ST/FL2/FL3`
（`ToneCurveName2012=Linear`、所有滑桿 0、關鏡頭檔）比對。以亮度分位配準，
中亮度區（L\* 25–90）三場景平均：

| 機內 | 參考 | ΔL | ΔC |
|---|---:|---:|---:|
| ST | Adobe ST | **+0.50** | −0.43 |
| FL2 | Adobe **ST** | **+2.53** | −8.01 |
| FL2 | Adobe FL2 | **−8.25** | −2.15 |
| FL3 | Adobe **ST** | **−0.23** | −4.75 |
| FL3 | Adobe FL3 | **−9.50** | −2.93 |

機內 FL2／FL3 的色調**落在 Adobe 的 ST 上**，而不是 Adobe 的 FL2／FL3。
Adobe 側真正的外觀差異是 ST→FL2 −10.16、ST→FL3 −9.06，機內完全沒做出來。
也就是說：0.5.1 換了曲線內容卻毫無變化，因為那四條記錄從頭到尾沒被讀取。

## 取用鏈（全部由反彙編取得）

```
0x323128  resolve_gamma_row(params, still_movie, out, out)
  ├ 0x323160  r0 = params[0xc]                  ← CP color 索引
  ├ 0x323172  bl 0x138832                       ← 回傳 r1 = 路由表基址
  ├ 0x32317a  r0 = r1 + r0*8 + r4*4             ← r4: 0=照片 1=影片
  ├ 0x323184  row = *(u32*)r0
  └ 0x323186  *out = row

0x32344c  fetch_record(ctx)
  ├ 0x32345a  fp = 0x01209480                   ← 追加的指標表
  ├ 0x32346c  r0 = row*7
  └ 0x323474  record = fp[row*7 + internal_slot]
```

- **指標表**（列 → 7 筆記錄指標）：原廠 RAM `0x01108d0c`，0.4.0 起 5 處
  （`0x32345a`、`0x323d82`、`0x323dd0`、`0x323eb6`、`0x9cf436`）全部改到
  追加表的 `0x01209480`。掃描 `movw/movt` 常數確認**沒有殘留**。
- **路由表**（color → (照片列, 影片列)，步長 8）：原廠 RAM `0x00e02580`，
  原來 3 處（`0x323172`、`0x3231da`、`0x323298`）。前兩處被換成
  `bl 0x138832`，第三處直接改成 `0x012099f8`。**也都沒有殘留。**

## 根因：helper 把照片的 color 索引改寫成 0

`0x138832` 是 26 位元組的葉子函式（原先是外觀描述符建構器的一段，被就地改寫）。
0.5.1 的內容：

```text
0x138832: cmp  r4, #0
0x138834: bne  0x138840          ; r4 != 0 → 跳過
0x138836: cmp  r0, #0x13
0x138838: blo  0x138840          ; r0 < 19 → 跳過
0x13883a: cmp  r0, #0x14
0x13883c: it   ls
0x13883e: movls r0, #0           ; ← 19 ≤ r0 ≤ 20 時把 color 索引歸零
0x138840: movw r1, #0x99f8
0x138844: movt r1, #0x120        ; r1 = 0x012099F8（追加的路由表）✓
0x138848: bx   lr
```

基址是對的，但索引被歸零。

**r4 是照片／影片選擇器**，`r4 == 0` 是照片：

- `0x323188` 的 `bne` 只在 `r4 == 1` 時執行讀取 `+4`（第二元素＝影片）的分支；
- `r4` 來自 `0x3233b4` 的 `uxtb r1, r0`，而 `r0` 是 `bl 0x9ce804` 的回傳值
  `(params[4] != 0) && (params[0x2c] != 1)`，`params[4]` 為 0 即照片。

所以只有**照片**會被歸零：FL2／FL3 照片拿到 `route[0] = (0, 10)` → 第 0 列
→ 原廠 `0xE02910`（ST 的槽 6 記錄）。影片（`r4 == 1`）不受影響，本來就走
第 48／49 列。

**CP color 索引 19／20 確實是 FL2／FL3**，由 `sony-a7m4-custom-firmware` 方法 3
交叉驗證：其 README 的對應表記載 FL2 → CP color 19、FL3 → CP color 20，且
appFw.so 側要把 look 10/11 發成 color 19/20。本專案的 appFw.so 也有對應寫入
（`0x3528804` 112 位元組，以及 `0x4b4a5e4→0x0a`、`0x4b4a5ec→0x0b` 啟用 look 10/11）。

## 修正

把前 14 位元組整段換成 NOP，保留 `movw/movt` 與 `bx lr`：

```text
0x138832: nop ×7
0x138840: movw r1, #0x99f8
0x138844: movt r1, #0x120
0x138848: bx   lr
0x13884a: nop
```

原地改寫，窗口仍是 26 位元組，模組長度 56864 位元組不變，重定位不變。
Gamma 窗口、色彩資產、其餘所有窗口均未動。cpapp-b.bin 最終雜湊
`a969a783…` → `30a595529fe842244da735c0602ca8a379a911e1d79340c624ae1f04d550f342`。

## 端到端模擬（`work/tools/verify_route_052.py`）

| color | 照片/影片 | 列 | 內部槽 | 取到的曲線 |
|---:|---|---:|---:|---|
| 19 (FL2) | 照片 | 48 | 0 / 6 | FX2 **FL2 照片槽 6** (gen 5 / 6) |
| 19 (FL2) | 影片 | 48 | 0 / 6 | FX2 **FL2 照片槽 6** |
| 20 (FL3) | 照片 | 49 | 0 / 6 | FX2 **FL3 照片槽 6** (gen 5 / 6) |
| 20 (FL3) | 影片 | 49 | 0 / 6 | FX2 **FL3 照片槽 6** |

修復前：color 19/20 → 0 → `route[0] = (0,10)` → 第 0 列 → `0xE02910`（原廠 ST）。

## 驗證界限

- 靜態證據完整（取用鏈、r4 語意、color 編號有 A7M4 交叉驗證），並有端到端模擬。
- **尚未重新上機實拍**。預期機內 FL2／FL3 的 ΔL 從 −8.25／−9.50 收斂到接近
  ST 對照的 ±1；若沒有，則表示 color 索引不是 19/20，需要再查 appFw.so 的路由。
- 影片與照片仍共用同一條曲線（原廠路由把兩者指到同一列；追加表第 19/20 項
  都是 (48,48)／(49,49)）。FX2 另有影片曲線，但 A7C II 沒有落點。
