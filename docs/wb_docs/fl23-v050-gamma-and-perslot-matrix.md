# 0.5.0：Gamma 內部槽 6 改用照片曲線、矩陣改為逐槽複製

本文件說明 0.5.0 相對 0.4.0 改了什麼、怎麼從解包的韌體推出結論、以及哪些部分仍然未知。

一句話結論：**Gamma 的四條記錄改為 FX2 的照片曲線（原先 generation 6 那兩條誤用影片曲線）；矩陣的 48 個槽不再「每端點 16 槽同值」，改為逐槽複製 FX2 供體值。色度一個位元組都沒動。**

## 2. Gamma：槽 6 該用哪一條曲線

### 2.1 A7C II 的 Gamma 記錄長什麼樣

A7C II 2.01 原廠 CP（`cpapp-b.bin`）的 Gamma 表在 `+0xcfa6d0`，步長 0x240（576 位元組），共 50 條記錄：

```text
+0x218  tag   高字节 = Gamma ID（0x00 … 0x2d）
+0x21c  gen   5 = 內部槽 0～5 共用；6 = 內部槽 6
+0x220  max   曲線終點
+0x23c        結構欄位，原廠記錄一律是 2
```

每條記錄前 516 位元組是 129 個 u32 取樣點。同一個 ID 最多兩條（gen 5 與 gen 6）。

### 2.2 原廠路由表已經指定 FL2／FL3 的 ID

`cpapp-b.bin +0xcfa588` 有 20 組「(照片 Gamma ID, 影片 Gamma ID)」，**原廠 2.01 就存在**，最後兩組是：

```text
… (0x27,0x2b) (0x28,0x2c) (0x30,0x30) (0x31,0x31)
```

也就是索尼自己的 A7C II 把 FL2 的照片與影片都指到 ID 0x30、FL3 都指到 ID 0x31。其餘外觀常見「影片 ID = 照片 ID + 0x0a」（例如 0x00／0x0a、0x25／0x29），FL2／FL3 是少數共用同一個 ID 的。因此 A7C II 的 FL2／FL3 只需要兩條記錄（gen 5 與 gen 6），不是三條。

這條資料同時證實 0.4.0 選用的 ID（0x30／0x31）是正確的。

### 2.3 FX2 同一個 ID 下面是照片曲線

FX2 1.01 的 Gamma 表在 `+0xdac174`，步長 580 位元組，共 56 條：

| FX2 偏移 | ID | gen | max | 前四點 | 用途 |
|---|---:|---:|---:|---|---|
| `0xdb32bc` | 0x30 | 3 | 130944 | 0, 576, 1155, 1736 | FL2 照片槽 0～5 |
| `0xdb3500` | 0x30 | 6 | 130944 | 0, 1158, 2316, 3474 | **FL2 照片槽 6** |
| `0xdb3744` | 0x31 | 3 | 130945 | 0, 632, 1271, 1913 | FL3 照片槽 0～5 |
| `0xdb3988` | 0x31 | 6 | 130945 | 0, 1282, 2564, 3845 | **FL3 照片槽 6** |
| `0xdb3bcc` | 0x32 | 6 | 122844 | 0, 1085, 2171, 3256 | FL2 影片槽 6 |
| `0xdb3e10` | 0x33 | 6 | 122753 | 0, 1202, 2403, 3605 | FL3 影片槽 6 |

R5 研究文件第三節的換算表寫明 **RAW 0x7806 = 2 × CP 照片 Gamma 內部槽 6**，並給出「FL2 前 8 點 CP = `[0,1158,2316,3474,…]`」——正是上表 `0xdb3500` 那一條。也就是「這個外觀的曲線」指的是照片槽 6，不是影片槽 6。

### 2.4 0.4.0 錯在哪

0.4.0 的四條記錄中，gen 5 的兩條（槽 0～5）正確等於 FX2 `0xdb32bc`／`0xdb3744`；**gen 6 的兩條等於 FX2 的影片曲線 `0xdb3bcc`／`0xdb3e10`**（前四點 0,1085,… 與 0,1202,…，max 122844／122753）。因為 A7C II 的照片與影片共用 ID 0x30／0x31，照片在內部槽 6 也就拿到影片曲線了。

0.5.0 把這兩條換成 `0xdb3500`／`0xdb3988`。

### 2.5 580 → 576 的換算（已被兩條舊記錄逐位元組證實）

```text
A7C II 記錄(576B) = FX2[0:0x238] + FX2[0x23c:0x244]
再把 +0x21c 的 gen 由 FX2 的 3 改為 5（槽 0～5 那條）
```

以這個公式重建 FX2 `0xdb32bc`（gen 3→5）與 `0xdb3744`（gen 3→5），與 0.4.0 現有的第 0、2 條記錄**逐位元組相同、零差異**；第 1、3 條則不同，正是本次修正之處。FX2 記錄尾端的 u32（+0x240）在兩個外觀上都是 2，換算後落在 A7C II 的 `+0x23c`，也與原廠記錄的 2 相符。

### 2.6 改了哪些位元組

| 視窗 | 長度 | 變化 |
|---|---:|---:|
| `cpapp-b.bin +0x1100b80` | 3872 | 514 |

3872 位元組 = 4 條記錄（4 × 576 = 2304）+ 指針表與路由表（1664）。後半部（指針表、20 組路由）完全沒動，`fl23_color`/`tests` 以 `TAIL_SHA256` 固定它。

`cpapp-b.bin` 的完整 SHA-256 由 `60a9de1a…` 變為 `9bbaa6c5…`；`core.FINAL[1]`、`native/patch_manifest.h` 的 `final_hashes[1]`，以及 `installer.so` 內同一處 32 位元組一起更新。**`installer.so` 是以等長位元組取代同步的**：`new_0`（3872 位元組）與 `final_hashes[1]`（32 位元組）在模組中各只出現一次，原址覆寫後模組大小與所有重定位都不變（56864 位元組）。若要改用 `zig cc` 重新編譯，`BUILD.md` 的指令仍然適用，但工具鏈差異會讓整個模組的位元組不同，需重新驗證。

### 2.7 仍然未知／已知取捨

- **影片會跟著用照片曲線。** 這是 2.2 節原廠路由的直接結果：A7C II 的 FL2／FL3 照片與影片共用一個 Gamma ID，沒有第二個 ID 可放影片曲線（指針表只到 ID 0～49，0x32／0x33 已在表外）。要讓影片也對，得改寫原廠路由表與指針表，風險遠大於收益，本次不做。
- **槽 0～5 與槽 6 的分工沒有實機量測。** 「照片走哪一條」是 R5 研究文件對 RAW 0x7806 的結論，加上原廠路由的旁證；沒有在機上逐模式量測。
- **Knee 相關三個指針仍為零**，走韌體預設（512／1024），與 R5 研究的 FL2／FL3 目標相同，未改。

## 3. 色彩：16 個槽是色相分區，不是冗餘

### 3.1 判據

576 位元組的 block13 記錄 = 3 個光源端點 × 192 位元組，每端點 16 槽 × 12 位元組六係數。0.4.x 把每個端點的 16 槽填成同一組係數，理由是「逐槽供體值沒有公開來源」。這個理由不成立：

1. **A7C II 自己的原生外觀就是逐槽不同的。** 讀原廠 `unit-02a4000d`（`FlashDir/backup1.2/original/`），每個 bank 的每個端點都有 15～16 個不同的槽值（bank 16 是 `[15,16,16]`，bank 8 是 `[15,1,16]`，其餘多是 `[16,16,16]`）。若 16 槽只是備援，原廠不必存 16 組不同值。
2. **0x780F 是按這 16 槽逐槽打包的。** R5 研究文件第四節：RAW 0x780F 的 `[24,216)` 就是「group1 的 16 槽 × 6 係數，按列重排 ×4」；`[0,24)` 是「16 段色相分區座標」。把 16 槽填成同值，等於把 16 段色相分區全部用同一個判讀，也正是使用者回饋「色相改不動」的成因。
3. **FX2 供體本來就有這 48 組值。** `work/fx2_unit0d_CX96900_.bin` 的 `0x1e0 + bank*768`（FL2 = bank 22 → `0x43e0`，FL3 = bank 24 → `0x49e0`）直接就有，bank 尾端 192 位元組在 FX2 與 A7C II 都是零，所以只取前 576 位元組即可。

### 3.2 改了什麼

| 外觀 | 參數／槽 | 色度 | 矩陣 | 合計 | 矩陣記錄 SHA-256（前 16） |
|---|---|---:|---:|---:|---|
| FL2 | 55／23 | 0 | 346 | 346 | `7a15baf6…` → `753e57f9…` |
| FL3 | 56／25 | 0 | 323 | 323 | `d2783261…` → `a5b7d763…` |
| 合計 | | 0 | 669 | **669** | |

**色度完全沒動。** 把 FX2 CC1 的絕對三組 A／B／C 轉成差分（A、B−A、C−A）後，與 0.4.0 已在使用的 R5 公布值逐項相同——兩份獨立來源互相印證，不需要改。

### 3.3 交叉驗證

`fl23_color.py verify` 會重跑（全部通過）：

- 48 個槽逐位元組等於 `assets/fx2_fl23_donor.json`；
- 每個槽展開成 3×3 後三行行和都是 1024（中性輸入不偏色）；
- **A1 端點槽 0 等於 R5 公布的六係數**，B／A2 端點槽 0 等於 A7M4 專案公布的端點值——供體、R5、A7M4 三份來源在槽 0 上一致，端點順序因此得到印證；
- 色度等於 FX2 差分值，也等於 R5 公布值。

### 3.4 預期方向（代數試算，非機內像素）

`python fl23_color.py hue --per-slot` 會列出 A1 端點 16 個色相分區各自的位移，並同時給出「與槽 0 的差」，也就是 0.4.x 全槽同值時失去的量。FL2 在 L\*=55、C\*=45 取樣下，各分區相對槽 0 的差異最大可達約 40 度（例如輸入 180° 時槽 14 比槽 0 多推約 40 度；輸入 60° 時槽 4 多推約 17 度）。

這仍是「矩陣作用在線性 sRGB 上」的近似：不含去馬賽克、白平衡、Gamma 與色度階段，不代表機內最終像素，只看方向與相對大小。

## 5. 自檢

```text
python fl23_color.py inspect            # 48/48 槽等於供體值、各端點不同槽值數
python fl23_color.py verify             # 逐槽、行和、A1 與 R5 一致、清單雜湊
python fl23_color.py hue --per-slot     # 逐色相分區的位移與 0.4.x 的落差
python -m unittest discover -s tests    # 46 項離線測試
python app.py check-package
```

`fl23_color.py port --fill endpoints` 可重建 0.4.0 的記錄，`--fill unified`／`--fill primary` 可重建 0.3.x／0.2.0，只供回退比對；正式資產一律用預設的 `perslot`。

## 6. 驗證邊界

- 本次是純離線變更：沒有寫相機、沒有重拍、沒有測色。改動只證明「記錄已等於 FX2 供體值、Gamma 槽 6 已是照片曲線」，不證明畫面等於 FX2 或 A7R V。
- 「16 槽 = 色相分區」是結構推論（原生外觀逐槽不同 + 0x780F 的打包方式），不是機上逐分區量測。
- 「照片走槽 6」來自 R5 對 RAW 0x7806 的對照，未在本機逐模式驗證；影片改用照片曲線是原廠共用 ID 的必然結果，實拍影片時應分開判斷。
- `installer.so` 是等長位元組取代，未重新編譯；模組大小不變，但這是位元組層面的同步，不是工具鏈重建。上機前仍應以 `check-package` 與原廠程式雜湊再次確認。
- 0.1.0 至 0.4.0 的 ZIP 全部保留，可隨時回退比對。
